# 媒体整理（mediaorganize）四个缺陷分析报告

- **分支**：`fix/organize-bug-analysis`（基于 `main` @ `42a3ee9`）
- **涉及模块**：`internal/mediaorganize/**`、`internal/classifyorganize/**`
- **验证方式**：为每个缺陷写了可复现的 planner 级测试（见文末「复现方法」），全部编译通过并复现出错误计划。

## 结论速览

| # | 现象 | 根因一句话 | 状态 |
|---|---|---|---|
| 1 | 人工匹配后 TV/Movie 标签丢失，文件落到任务根目录 | 手动匹配的重规划器 **没有注入分类增强器**（`service_binding.go:91`），`classifyGroup` 直接返回空 Decision | **已复现** |
| 2 | 批量处理时有概率落到任务根目录 | 分类**执行失败**（`Matched=false`）时，`classificationParentRef` 把父目录**降级为移动根目录**，且降级是静默的 | **已复现** |
| 3 | 根目录散落的 `movie.mkv` 不建目录 | 分类不可用/未命中时作品目录**少了「电影/电视剧」这一层**，父目录塌缩到 `targetRootID`（很多配置下就是网盘根） | **已复现（塌缩版）**，见 §3 说明 |
| 4 | 年份被当成硬性红线 | `PickTMDBMatchForYear` 里 `if expectedYear != nil { … return nil }`，年份不同直接判负，放弃「唯一强匹配」 | **已复现** |

Bug 1/2/3 **是同一个设计缺陷的三个出口**：分类（`classifyorganize`）被当成了「可选的锦上添花」，而不是「决定目标路径的必需环节」。它失败时的兜底策略是 **把作品目录直接塞到移动根目录下**，而移动根目录往往就是用户配的网盘根目录。

## Bug 1：人工匹配后标签丢失、文件落到任务根目录

### 根因

增强器（classification / recognition）只在**一个地方**被注入 planner：

```
internal/app/wire_mediaorganize.go:121   p.SetRecognitionEnhancer(a.recognition)
internal/app/wire_mediaorganize.go:122   p.SetClassificationEnhancer(a.classification)
```

而「人工匹配后重规划」这条路径自己 new 了一个 planner，**没做同样的注入**：

`internal/mediaorganize/service_binding.go:70-104`

```go
func (s *Service) replanMatchedGroup(...) (*Plan, error) {
    ...
    p := planner.New(          // :91
        ctx, s.files, accountID,
        planner.TaskConfigFromMap(cfg),
        plannerSettings, taskID, tmdbClient,
        func(string) {}, nil, func() error { return nil },
    )                          // ← 没有 p.SetClassificationEnhancer / SetRecognitionEnhancer
    return p.ReplanMatchedGroup(group, raw)   // :103
}
```

`internal/mediaorganize/service.go` 的 `Service` 结构体上**根本没有 classification 字段**（`grep -rn "classification" internal/mediaorganize/service.go` 无结果），所以不是「忘了调用」而是「这条路径拿不到依赖」。

### 连锁反应

`internal/mediaorganize/planner/classification.go:13-14`

```go
func (p *Planner) classifyGroup(mediaType, tmdbID string, raw map[string]any) classification.Decision {
    if p.actionType != "move" || p.classification == nil || !p.classification.Available() {
        return classification.Decision{}   // 全零 Decision：Applied=false, Matched=false
    }
```

拿到全零 Decision 之后：

1. `internal/mediaorganize/planner/actions.go:88-93`（`ensureWorkDirAction`）
   ```go
   if classificationDecision.Applied {
       parentRef = p.classificationParentRef(classificationDecision)
   } else {
       categoryAncestors := p.categoryAncestors(key, items)
       parentRef = p.buildTargetCategoryParentRef(categoryAncestors)   // 根目录散落文件 → ancestors 为空
   }
   ```
   散落文件没有 ancestors ⇒ `buildTargetCategoryParentRef` 的循环一次都不执行 ⇒ **作品目录直接挂在 `p.targetRootID` 上**。

2. `internal/mediaorganize/planner/classification.go:85-88`（`classificationMetadata`）
   ```go
   if !decision.Applied { return nil }
   ```
   ⇒ action 的 `Metadata` 里 **完全没有 `classification_applied` / `classification_category` / `classification_matched`**，前端预览自然「看不到 TV/Movie 标签」。

### 实际产出（复现输出）

以 `阿凡达 (2009).mkv` 散落在扫描根、人工匹配到 tmdb-19995 为例：

```
[a1] ensure_dir  TargetParentID="target"  TargetName="阿凡达 (2009)"
     （"target" = 移动根目录，直接少了 电影 这一层）
[a2] relocate    阿凡达.2009.mkv -> ref:a1/阿凡达 (2009).mkv
     meta = { media_kind: movie, tmdb_id: 19995 }      ← 没有任何 classification_* 字段
```

对比走正常 `Build()` 路径（enhancer 正常）的结果：

```
[a1] ensure_dir  target/电影
[a2] ensure_dir  ref:a1/阿凡达 (2009) {tmdb-19995}   meta={is_work_dir:true, classification_category:电影, ...}
[a3] relocate    -> ref:a2/阿凡达 (2009).mkv
```

### 修改建议

**A. 首选：让 `Service` 持有增强器，所有建 planner 的地方统一注入。**

在 `internal/mediaorganize/service.go` 的 `Service` 上加字段：

```go
type Service struct {
    ...
    classification classification.Enhancer
    recognition    recognition.Enhancer
}
```

并在 `internal/app/wire_mediaorganize.go` 里 `plannerAdapter.Build` 之外、构造 `Service` 的地方注入。然后把 planner 的构造收敛成一个方法，所有路径共用：

```go
// internal/mediaorganize/service_binding.go
func (s *Service) newPlanner(ctx context.Context, taskID string, task *domain.MediaOrganizeTask,
    cfg map[string]any, settingsDict map[string]any) *planner.Planner {
    ...
    p := planner.New(ctx, s.files, accountID, planner.TaskConfigFromMap(cfg), plannerSettings, taskID, tmdbClient, logFn, nil, stopFn)
    p.SetRecognitionEnhancer(s.recognition)      // 新增
    p.SetClassificationEnhancer(s.classification) // 新增
    return p
}
```

`replanMatchedGroup`、`buildPlan`（`service.go`）都改为调用 `s.newPlanner(...)`。这样以后再加增强器不会再漏。

**B. 兜底：`classifyGroup` 的 nil 判断不应静默返回全零。**

`internal/mediaorganize/planner/classification.go:14` 现在是「什么都不记」。建议区分两种失败：

```go
if p.actionType != "move" {
    return classification.Decision{}
}
if p.classification == nil || !p.classification.Available() {
    p.recordClassificationDegraded("classification_unavailable")  // 记进 diagnostics，预览里可见
    return classification.Decision{Applied: true, Matched: false, DegradedReason: "classification_unavailable"}
}
```

这样即使拿不到增强器，也不会「假装什么都没发生」，运维/用户能在计划预览和诊断里看到原因。

**C. `replanMatchedGroup` 传给 `ReplanMatchedGroup` 的 `raw` 不完整。**

`ApplyBindingToPlan` 传的是 TMDB **搜索结果**（`results[0]`），`classifyorganize.loadDetail` 需要的是 **detail 接口**（`genres` / `origin_country`）。默认模板（只判 `type`）不受影响，但**地区/类型模板会必然降级**。建议：`ReplanMatchedGroup` 内部若 `raw` 缺 `genres`/`origin_country`，通过 `p.Lookup(ctx, tmdbID, mediaKind)`（`classification.go:43`）补一次 detail 再 classify。

## Bug 2：批量处理时有概率落到任务根目录

### 根因

这是 Bug 1 的「偶发版本」。批量场景下分类服务是**真的被调用了**，但会因为**每一次调用的成败不同**而表现不同，于是表现为「有概率」。

`internal/classifyorganize/service.go` 的 `Classify` 在需要 TMDB 详情时走 `loadDetail`；一旦详情拿不到（例如该条目没匹配到 tmdb id → `req.TMDBID == ""`，或 TMDB 请求限流/失败），`state.degradedReason` 变成 `tmdb_detail_unavailable`，`Matched=false`。

回到 `internal/mediaorganize/planner/classification.go:68-74`：

```go
func (p *Planner) classificationParentRef(decision classification.Decision) string {
    parentRef := p.targetRootID
    if parentRef == "" {
        parentRef = p.parentID
    }
    if !decision.Matched {
        return parentRef          // ← 未命中 = 直接用移动根目录当父目录
    }
    for _, segment := range decision.RelativeSegments { ... }
    return parentRef
}
```

**关键缺陷：把「分类失败」等同于「应该放在根目录」。** 这两件事没有任何逻辑关系。分类失败只是意味着「我不知道该放哪儿」，正确做法应该是：

1. 回退到 `categoryAncestors` / `buildTargetCategoryParentRef`（保留源目录的分类层级），或
2. 至少回退到 media kind 的兜底分类（movie → 电影，tv → 电视剧），或
3. 明确把这类条目标记为 `needs_match` / `needs_classification`，**不让它静默落到根目录**。

### 实际产出（复现输出）

一个任务里有 3 个电影目录：两个能匹配到 TMDB 且分类成功，第三个匹配不上 TMDB。分类 stub 对 `req.TMDBID==""` 返回 `Matched=false, DegradedReason:"tmdb_detail_unavailable"`：

```
[a1] ensure_dir              -> target/电影
[a2] ensure_dir  is_work_dir -> ref:a1/国产
[a3] move_and_rename_dir     ref:a2/阿凡达 (2009) {tmdb-19995}      ✅
[a5] move_and_rename_dir     ref:a2/流浪地球 (2019) {tmdb-157350}   ✅
[a7] move_and_rename_dir     src=d3 某未知片子 (2018) -> target=target/某未知片子 (2018)
     meta={classification_applied:true, classification_matched:false, classification_degraded_reason:tmdb_detail_unavailable}
     ❌ 直接挂在 target（移动根目录）下，没有 电影/国产 这两层
```

同一批任务、同一个开关，前两个进分类目录、第三个进根目录 —— 就是用户看到的「有概率」。

### 为什么是「有概率」而不是必然

分类结果的分布取决于以下任一因素，都会让同一批任务结果不同：

- 分类模板类型：默认 `TemplateMedia`（只判 `type`，**无 TMDB ID 也能命中**）；一旦用户改成 `TemplateRegion` / `TemplateGenre` / 自定义模板，命中就强依赖 TMDB 详情 → 变成「有的条目命中、有的不命中」。
- TMDB 详情缓存：`loadDetail` 有 30 分钟缓存（`detailCacheTTL`）和 `maxDetailCache = 256` 的容量上限，**跑批过程中后段的条目会频繁 miss** ⇒ 「前面的进分类目录、后面的进根目录」。
- TMDB 限流/网络抖动：`degradedReason` 变化 ⇒ 命中变化。

### 修改建议

**A. 区分「没分类」和「分类了但没命中」两种状态，落到不同的兜底。**

在 `internal/mediaorganize/planner/classification.go`：

```go
func (p *Planner) classificationParentRef(decision classification.Decision) string {
    parentRef := p.targetRootID
    if parentRef == "" {
        parentRef = p.parentID
    }
    if !decision.Applied {
        // 分类器根本没跑：退回到源目录的分类层级，而不是根目录
        return p.buildTargetCategoryParentRef(p.categoryAncestorsForGroup)
    }
    if !decision.Matched {
        // 分类器跑了但没命中：按 mediaKind 做兜底分类（movie→电影 / tv→电视剧），
        // 并把条目记进 needs_classification，由用户决定
        if seg := mediaKindFallbackSegment(decision.MediaKind); seg != "" {
            return p.ensureDirAction(parentRef, seg)
        }
        return parentRef
    }
    ...
}
```

`classification.Decision` 需要补一个 `MediaKind` 字段（目前 `classifyGroup` 已经有 `mediaType` 入参，直接透传即可）。

**B. 把「分类降级」和「TMDB 未匹配」一样，登记成待处理项。**

`classifyGroup` 里已有 `recordClassificationDegraded(reason)`（`classification.go:52`），但它只写 `p.diagnostics["classification_degraded_reasons"]`，计划预览里看不到。仿照 `plan_group.go:404` 的 `recordNeedsMatch`，新增 `recordNeedsClassification(key, items, reason)`，让用户在预览里能一眼看到「这 12 个条目没进分类目录」。

**C. 顺手修掉 `classifyGroup` 缺少 `return` 的隐患（见 Bug 4 附带的同类问题）。**

**D. 提高 TMDB 详情缓存的稳定性。** `maxDetailCache = 256` 对大任务是硬伤；建议按 tmdb id 做 LRU 且容量与任务规模相关，或在跑批开始时预取所有需要的详情。

## Bug 3：根目录散落的 `movie.mkv` 不建目录

### 先说清楚实测结果（重要）

我按「文件名 × 目录结构 × move/rename × targetRootID 是否为空 × 分类开关/命中/未命中 × TMDB 命中与否」跑了 **96 组组合**，逐一 dump 计划。**planner 在所有组合下都会生成作品目录的 `ensure_dir`**，没有任何一组会生成「直接 relocate 到裸的网盘根目录」的动作：

| 组合 | 实际产出 |
|---|---|
| 散落 + move + 分类命中 | `target/电影/阿凡达 (2009) {tmdb-19995}/阿凡达 (2009).mkv` ✅ |
| 散落 + move + 分类**未命中/关闭** | `target/阿凡达 (2009) {tmdb-19995}/…` ⚠️ **少了 `电影` 这一层** |
| 散落 + move + 地区模板 + TMDB 未命中 | `target/阿凡达 (2009)/…` ⚠️ **同样少层** |
| 散落 + rename | `root/阿凡达 (2009) {tmdb-19995}/…` ✅ |
| `阿凡达 (2009)/` 目录 + move | `move_and_rename_dir d1 -> target/电影/阿凡达 (2009) {tmdb-19995}` ✅ |

所以「不建目录」这个现象**不是 planner 少生成了动作**，而是**目录建在了用户不想看到的地方**：当移动根目录被配置成网盘根（或根下的某个「下载/整理」目录）时，「作品目录直接挂在移动根下」在观感上就等于「扔到了根目录」，而且因为 `classificationMetadata` 返回 nil，计划里也没有任何分类标签可以佐证它本来该去 `电影/`。

这与 Bug 1、2 是**同一个出口**（`ensureWorkDirAction` 的父目录解析），只是触发条件更常见：只要分类不可用或未命中，任何散落文件都会走这条路。

### 相关代码

`internal/mediaorganize/planner/actions.go:87-94`

```go
parentRef := ""
if classificationDecision.Applied {
    parentRef = p.classificationParentRef(classificationDecision)
} else {
    categoryAncestors := p.categoryAncestors(key, items)
    parentRef = p.buildTargetCategoryParentRef(categoryAncestors)
}
ref := p.ensureDirAction(parentRef, workDirName)
```

`internal/mediaorganize/planner/actions.go:144-157`（`buildTargetCategoryParentRef`）：

```go
parentRef := p.targetRootID
if parentRef == "" { parentRef = p.parentID }
for _, anc := range categoryAncestors { ... }   // categoryAncestors 为空 → 原样返回 targetRootID
return parentRef
```

散落文件在 `internal/mediaorganize/planner/group.go` 的 `groupEntries` 里 `ancestors` 为空、`sourceDirID = p.parentID` ⇒ `categoryAncestors` 为空 ⇒ 父目录就是 `p.targetRootID`。

### 修改建议

**A. 散落文件（`key.dirID == ""`，即 `entry.sourceDirID == p.parentID`）必须走 media kind 兜底分类。**

这是最直接的修法：在 `ensureWorkDirAction` 里，当 `categoryAncestors` 为空**且**分类没提供 segments 时，用 `key.mediaKind` 兜底：

```go
if parentRef == p.targetRootID && len(categoryAncestors) == 0 {
    if seg := mediaKindFallbackSegment(key.mediaKind); seg != "" {
        parentRef = p.ensureDirAction(parentRef, seg)   // movie→"电影", tv→"电视剧"
    }
}
```

这样即使分类服务挂掉，散落文件也至少保证「作品目录在 `电影/` 或 `电视剧/` 里面」，永远不会裸露在根目录。

**B. 把「通用媒体目录」名单补全。** `internal/mediaorganize/rules/lexicon.go:18` 的 `GenericMediaDirNames` 目前只有：

```go
"电影", "影片", "movie", "movies", "电视剧", "剧集", "连续剧", "tv", "tv shows", "shows", "series",
"动漫", "动画", "anime", "media", "video", "videos", "视频",
```

**缺了最常见的落盘目录**：`下载`、`download`、`downloads`、`temp`、`tmp`、`未分类`、`其他`、`未整理`、`待整理`、`unsorted`。

后果：在 rename 模式下，文件位于 `/下载/阿凡达 (2009).mkv` 时，`internal/mediaorganize/planner/plan_group.go:426-430` 的

```go
func (p *Planner) renameNeedsWorkFolder(entry batchEntry) bool {
    ...
    return entry.sourceDirID == p.parentID || rules.IsGenericMediaDir(srcDirName)
}
```

判定为 false ⇒ **不建作品目录，只在原地重命名**。如果用户的「下载目录」就是网盘根或其近邻，观感就是「重命名完扔根目录」。建议至少补上 `下载` / `download(s)` / `temp` / `tmp` / `未分类` / `未整理` / `待整理`。

另外 `internal/mediaorganize/rules/tv.go:295` 的 `collectionContainerHintRe` 里有裸的 `/` 分支，**`IsCollectionContainerDir("/")` 恒为 true**，任何名字里带斜杠的目录都会被当成合集容器；这条建议一并加上「名字规范化后不能是空串或纯分隔符」的判断。

**C. 兜底断言：不允许「作品目录直接挂在移动根」在没有分类依据时发生。**

在 `finalize()`（`internal/mediaorganize/planner/planner.go`）加一道自检：凡是带 `is_work_dir` 元数据、且 `TargetParentID` 等于 `p.targetRootID`、同时又没有 `classification_matched:true` 的 `ensure_dir`，写入 `p.diagnostics["work_dir_without_category"]` 并在计划预览里提示。这样用户一眼能看到「有 N 个作品目录没有进分类目录」。

**D. executor 侧：把「没有分类父目录」变成显式失败而不是静默根目录。**

`internal/mediaorganize/executor/executor.go` 的 `execEnsureDir` 在父目录无法解析时会标记 `目标父目录未解析`，这个行为是对的；建议同样加一条：若动作带 `is_work_dir` 且最终 `TargetParentID` 解析到了移动根，跳过执行并回报原因，避免真的落地到根目录。

## Bug 4：年份被当成硬性红线

### 根因

`internal/mediaorganize/rules/tmdb.go:142`（`PickTMDBMatchForYear`）：

```go
func PickTMDBMatchForYear(results []map[string]any, expectedYear *int, mediaType, queryTitle string) map[string]any {
    ...
    if expectedYear != nil {
        for ... {
            if resultYear != nil && *resultYear == *expectedYear && compatible(item) {
                return item
            }
        }
        return nil          // ← 年份不同 = 直接判负，不看标题是否唯一强匹配
    }
    ...
}
```

`internal/mediaorganize/rules/tmdb.go:175`（`PickTMDBSearchMatchForYear`）的「宽松」分支同样要求年份相等。

`internal/mediaorganize/planner/tmdb_match.go:214-239`（`tmdbTryMatch`）：

```go
selected := rules.PickTMDBSearchMatchForYear(maps, year, mediaType, title)   // :224
if selected == nil && year != nil {
    mapsNoYear, err := p.tmdb.Search(p.ctx, title, nil, mediaType)            // 去掉年份重搜
    if err == nil {
        if selected2 := rules.PickTMDBSearchMatchForYear(mapsNoYear, year, mediaType, title); selected2 != nil {
            selected = selected2
        }
    }
    if selected == nil {
        return nil, nil                                                        // :237 二次判负
    }
}
```

也就是说：**去掉年份重搜之后，仍然用同一个年份门槛去筛**，等于白搜。年份不同就彻底放弃匹配。

更讽刺的是，同文件 `internal/mediaorganize/rules/tmdb.go:192` 已经有一个现成的「相邻年份唯一匹配」函数 `PickUniqueTMDBAdjacentYearMatch(results, expectedYear, mediaType, queryTitle)`，但**主匹配链路从未调用它**。

### 实际产出（复现输出）

单元级：
```
rules.PickTMDBMatchForYear([阿凡达 2009], 2010, "movie", "阿凡达")        => nil
rules.PickTMDBSearchMatchForYear([阿凡达 2009], 2010, "movie", "阿凡达")  => nil
rules.PickUniqueTMDBAdjacentYearMatch([阿凡达 2009], &2010, "movie", "阿凡达") => 阿凡达 ✅（没人调用）
rules.PickTMDBMatchForYear(nil, 2010, "movie", "阿凡达")                 => 阿凡达 ✅（证明差异只来自年份）
```

端到端：目录 `阿凡达 (2010)` + 文件 `阿凡达.2010.1080p.mkv`，TMDB 带年份搜不到、不带年份搜到 2009 年的《阿凡达》⇒ 计划把它重命名/移动为 **`阿凡达 (2010)`（没有 `{tmdb-19995}`）**，同时记一条 `needs_match`「TMDB 未匹配到影片，可手动选择」。

实际伤害：**年份被文件名里的错误年份带偏 → 匹配失败 → 目录名/文件名被"修正"成一个错的年份 → 之后每次整理都重复匹配失败**。

### 修改建议

**A. 年份从「红线」降级为「加权项」。**

`internal/mediaorganize/rules/tmdb.go:142` 改成三档策略：

```go
func PickTMDBMatchForYear(results []map[string]any, expectedYear *int, mediaType, queryTitle string) map[string]any {
    // 1) 年份精确命中（保持原逻辑）
    // 2) 年份不同，但标题唯一强匹配（IsTMDBTitleCompatible 命中 + 候选里只剩 1 个）→ 接受
    //    并把 Confidence 降级（见 D）
    if expectedYear != nil {
        for ... { if resultYear != nil && *resultYear == *expectedYear && compatible(item) { return item } }
        if m := rules.PickUniqueTMDBAdjacentYearMatch(results, expectedYear, mediaType, queryTitle); m != nil {
            return m
        }
        return nil
    }
    ...
}
```

**B. 候选不唯一时，用标题相似度打破平局，而不是一刀切。**

复用已有的 `rules.ScoreTitleForTMDB(title)`（`tmdb.go:317`）和 `IsTMDBTitleCompatible`（`tmdb.go:48`）：在年份不命中的候选里，取标题兼容且分数最高的一个；当 top1 与 top2 分差 ≥ 阈值时才接受，否则才判歧义（交给 `detectMultiVersionAmbiguity` 走人工选择）。

**C. `tmdbTryMatch` 的第二次搜索不要复用年份门槛。**

`internal/mediaorganize/planner/tmdb_match.go:234` 改为：

```go
// 无年份候选：先用完整年份门槛找，找不到再退到"唯一标题匹配"
if selected2 := rules.PickTMDBSearchMatchForYear(mapsNoYear, year, mediaType, title); selected2 != nil {
    selected = selected2
} else if m := rules.PickTMDBSearchMatchRelaxed(mapsNoYear, mediaType, title); m != nil {
    selected = m   // Relaxed：忽略年份，但要求标题强匹配 + 唯一
}
```

（`PickTMDBSearchMatchRelaxed` 是新增函数，语义 = 年份不参与打分，仅 `IsTMDBTitleCompatible` + 唯一性。）

**D. 置信度分层，让 UI 能展示「年份可能不准」。**

匹配到但年份不符时，置信度取现有两档的中间值（现在只有命中 `0.9` / 年份不符 `0.65` 两档，见 `tmdbMatchResult.confidenceOr`，`tmdb_match.go:29`），并加一个 `year_mismatch: true` 标记。目录名用 **TMDB 的真实年份**（`阿凡达 (2009) {tmdb-19995}`）而不是文件名里的错误年份，这样一次整理就把名字纠正了，后续不再重复失败。

**E. `needs_match` 的文案要区分「真的没有」和「年份挡住了」。**

`internal/mediaorganize/planner/plan_group.go:105` 目前的 `recordNeedsMatch(key, items, "TMDB 未匹配到影片，可手动选择", nil)` 在年份被红线拦掉时也会出现，用户完全看不出原因。建议带上 `degraded_reason` / `year_mismatch_candidates`，让候选列表里出现「阿凡达 (2009) {tmdb-19995} —— 年份与文件名不一致」这种可一键采纳的项。

## 顺带发现的两个隐患（本次未复现，但建议一并处理）

1. **`plan_group.go:105` 缺少 `return`。** TMDB 未匹配时 `recordNeedsMatch(...)` 之后没有 `return`，代码会带着空的 `tmdbID` 继续往下规划。这是「未匹配也照常整理」的根源，和 Bug 4 的修复方向一致，建议显式 `return nil` 或明确标注「未匹配时的降级规划」是有意为之（当前代码两可，容易被误读）。

2. **`conflicts.go:98-101` 的 `losingSourceID == ""` 分支只 `continue`、不重写依赖方。** 合并同名作品目录时，如果落败方的 `source_dir_id` 为空（散落文件），依赖它的 `relocate` 动作的 `ref:` 会变成悬空引用，执行时会以 `目标父目录未解析` 失败。修复方向：合并时把落败方的 `ensure_dir` 也保留（或直接把落败方 relocate 的 `TargetParentID` 改写为胜方 ref）。
